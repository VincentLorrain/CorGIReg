# JSON-driven graph transformation prototype

This external consumer is the starting point for a future rewrite engine. It
uses CorGIReg's public matching CLI and standalone generator. Recipe loading,
integer expressions, boundary mapping and graph replacement live here, outside
the CorGIReg library. No operator name or subtraction-specific wiring is built
into the runner.

## Run the example

Install the Python CLI and build the native commands first. From the repository
root, on PowerShell:

```powershell
.\build\install-venv\Scripts\python.exe examples/rewrite/recipe_runner.py --recipe examples/rewrite/recipes/subtract.json -i examples/rewrite/network.json -o build/transformed.json --matcher .\build\corgireg-match.exe --generator .\build\corgireg-generate.exe
```

On Linux, use the Python environment's `bin/python` and omit `.exe` from the
native commands. Installed SDK binaries can replace the build paths.

The output file is a normal graph JSON accepted by `corgireg -i`. A small audit
record on stderr reports the recipe, captured IDs, replacement IDs and resolved
repetition values. The output is written atomically only after validation;
errors leave an existing output untouched. The input object is not mutated.

## Recipe version 1

[subtract.json](recipes/subtract.json) matches `Sub#` and replaces it with
`Neg-2->Add#`. It maps the subtraction's input 1 to Add input 1, input 2 to
Neg input 1, and its output 1 to Add output 1. Every external consumer of that
output is reconnected, preserving its destination input number.

| Field | Contract |
| --- | --- |
| `schema_version` | Integer `1` |
| `name` | Nonempty recipe name; prefixes generated node names |
| `match` | Complete source pattern |
| `replacement.pattern` | Complete generation pattern |
| `replacement.repetitions` | Object keyed by one-based target quantifier indices |
| `replacement.default_output_port` | Explicit source output number for generated internal connections whose output is unspecified |
| `conditions` | Optional array of `{ "op": "even", "value": expression }` guards; all must pass |
| `inputs`, `outputs` | Arrays mapping matched boundary ports to replacement ports |

Each boundary entry has this shape:

```json
{
  "match": {"predicate": "Sub", "port": 1},
  "replacement": {"op": "Add", "port": 1}
}
```

Input mappings select the matched node's destination input; output mappings
select its source output. External producers' output numbers and external
consumers' input numbers are retained. `predicate` is the captured matching
predicate, while `op` identifies an operation generated by the target pattern.

Selectors default to a unique node. Optional `position: "first"` or `"last"`
selects from capture order (source) or generation order (replacement). Source
positions require exactly one contributing walk; no order is invented between
independent branches. Port values are positive 32-bit integers.

## Repetitions calculated from a match

[negate-chain.json](recipes/negate-chain.json) matches an even-length negation
chain and generates an identity chain with `n - 1` nodes:

```json
{
  "1": {
    "op": "subtract",
    "args": [{"quantifier": 1}, 1]
  }
}
```

This is the `replacement.repetitions` object. Values may be an integer,
an expression, or a list of expressions for successive nested invocations.
Supported arithmetic is `add`, `subtract`, and `multiply`, with two operands.
All results are integers between 0 and 1,000,000; expression depth is limited
to 32. The generator then validates `+`, `*`, and `?` bounds.

`{"quantifier": 1}` requires exactly one invocation of that source quantifier.
`{"quantifier": 1, "invocation": 0}` selects a zero-based invocation from a
single walk. Missing or ambiguous references are errors. No Python code or
free-form expression string is executed.

## Matching and replacement policy

One invocation applies one recipe to **one uniquely identified source subgraph**.
Guards filter matches first. Equivalent execution traces are grouped by their
captured node IDs; their resolved repetition values and boundary selections
must agree. Multiple distinct eligible subgraphs are rejected. No matching
subgraph produces an unchanged normalized graph with `changed: false`.

All incoming and outgoing boundary connections must be mapped. Unspecified
boundary ports, missing mappings, unused mappings, duplicate input producers
and target input collisions are rejected. Internal matched connections are
removed. Unaffected nodes retain their IDs, names and attributes; new nodes use
IDs above the original maximum, with overflow checked. An empty match cannot
be replaced. Exact duplicate connection records follow graph JSON normalization.

These rules deliberately expose ambiguity rather than silently scheduling
overlapping replacements. A future engine can add match selection, recipe
sequencing, richer predicates, attribute transfer and operator legality checks.
The current arithmetic recipes are examples, not formal equivalence proofs or
complete ONNX/StableHLO lowering rules.

## Tests and integration boundary

```sh
ctest --test-dir build -R Recipe_Rewrite_Integration --output-on-failure
ctest --test-dir build -R Installed_Package_Rewrite_Integration --output-on-failure
```

The nine Python tests verify exact reconnection, source immutability, unaffected
metadata, fanout, 48 scalar output comparisons, a multi-node match with derived
repetitions, another recipe without runner changes, no-op behavior, malformed
expressions, ambiguous matches, ID overflow and failed-output preservation.
They also write a transformed file and pattern-match it again.

The installed-package test reruns these recipes against relocated installed
native commands when Python is available. It uses this checkout's Python CLI
package through `PYTHONPATH`; the independent C++ consumer additionally verifies
`find_package(CorGIReg)` without source include paths.
